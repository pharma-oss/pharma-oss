# 開発・検証における行動ルール（嘘・誤魔化しの排除方針）

## 1. 型検査とビルドの厳格な実地検証
- **`npx tsx` に騙されない**: `npx tsx --test` は esbuild による高速トランスパイルのみを行うため型チェックをスキップする。
- **必ず `npx tsc --noEmit` を単独実行する**: TypeScript の型エラー（プロパティ非存在、型不一致等）が 0 件であることを自身の目で確認してから報告する。
- **本番ビルド `npm run build` を省略しない**: JSX 構文エラーやトランスパイルエラーを事前に検知する。

## 2. 真正なテストカバレッジの徹底
- **テストコード内でのロジック自前再実装（偽カバレッジ）を厳禁とする**:
  - テスト対象コンポーネントやモジュールの内部ロジックをテストファイル内で `.filter()` 等で再実装してテストした気になってはならない。
  - テスト対象のロジックは純粋関数（例: `calculateFilteredDrugs`）としてエクスポートし、本物の関数をテストファイルから直接 import して実地検証する。
- **テスト不在の領域を明視する**: 対象モジュールにテストが存在しない場合、「全体でN件通った」という数字をそのモジュールの正しさの根拠にしてはならない。

## 3. ドキュメントと実際のコードの完全整合
- コードの実態が伴っていない段階で、ドキュメントに「対応完了」と注記したりステータスを書き換えて取り繕う行為を完全に排除する。
- 指摘事項は、コードの修正・型検査・本物テスト通過のすべてが揃ってから初めて報告書を更新する。

## 4. ドメインロジック・仕様の文脈理解
- 表記の修正や検索最適化を行う際、ドメイン固有の仕様（処方モード `prescribed` での一般名【般】レコードの必要性、全件マスタに対する置換候補探索など）を損なわないよう、変更前後の挙動と副作用を精査する。

## 5. コマンド・ロックファイル更新の実地完了確認
- **`package-lock.json` と `node_modules` の完全更新を自身の目で確認する**: `package.json` の書き換えのみで満足せず、`npm install` / `npm ci` がエラーなく完了し `package-lock.json` が最新に再生成されていること、および `npm ci --dry-run` が通ることを必ず実地検証する。依存ライブラリの型更新に伴う全コンパイルエラーを `npx tsc --noEmit` で即座に検知・修正する。

## 6. プロジェクトスタイリング規約の遵守と UI の実表示検証
- **未導入のスタイリング手法（TailwindCSS等）を勝手に使用しない**: UI やバナーを作成する際は、既存コードベースのスタイル規約（Vanilla CSS、CSS変数 `var(...)` 、インライン style）を必ずコード検索で事前確認して遵守する。
- **表示崩れのない実画面・レイアウト検証**: レンダリング結果が無地・スタイル崩れにならないことをコンポーネント検証や開発サーバーでの表示確認で実地確認する。

## 7. 依頼されていない領域への独断的仕様・安全設計変更の厳禁
- **指示された範囲を超えて、基盤の競合解決・安全設計・ロジックを独断で書き換えてはならない**:
  - UX改善や課題指摘を受けた際、頼まれていない安全基盤や競合解決アルゴリズム（例: ハブ正本優先＋人間レビューから暗黙の Last-Write-Wins / 自動ファストフォーワードへの置き換え）を「気を利かせて」勝手にコード変更してはならない。
  - 医療データ（患者アレルギー・副作用・処方・薬歴等）の安全保護設計は最優先とし、変更の必要性を感じた場合は独断で実装せず、必ず事前に提案・対話として提示し合意を得る。
