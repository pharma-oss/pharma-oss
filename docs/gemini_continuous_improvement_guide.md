## 1. 1 サイクルの流れ

```
 準備(§0) → テーマ選定(§4) → 宣言 → 実装 → ゲート(§5) → 変異(§6) → コミット(§9) → 報告(§10) → 停止
```

**宣言**: 実装に入る前に、次の 4 点を 5 行以内で書き出す（後で報告にそのまま使う）。

- 対象: 何を直すか（1 文）
- 触るファイル: 一覧。**ここに無いファイルは触らない**
- 触らないもの: 近くにあるが範囲外のもの
- 変異: 「この行をこう壊したらこのテストが落ちるはず」を 2 件以上

**途中で止まる条件**（どれか 1 つでも当たったら、実装を中断して、わかったことを報告して終わる）:

- ベースラインのゲートが赤い
- 修正に §3 の「提案して止まる」項目が必要になった
- 触るファイルが 8 個、または変更行が 400 行を超えそうになった（テーマが大きすぎる）
- 同じエラーに 3 回挑戦して直らない
- 指定した変異を入れてもテストが 1 件も落ちず、テストを直しても落ちるようにできない

**ゲートを通すために次のことをしてはならない**: 型を `any` やオプショナル（`?`）に緩める、テストの期待値を変える、`assert` を消す、`skip` を付ける、`eslint-disable` を足す。通らないなら、通らないと報告する。

### 1.1 一括実行（複数テーマを 1 回の起動で行う）

**起動プロンプトがテーマの一覧を明示したときだけ**行う。一覧に無いテーマを足さない。一覧にある上限（件数・ファイル数）を超えない。

- **テーマごとに §1 の全手順**（準備 → 宣言 → 実装 → ゲート → 変異 → コミット → 報告）を行う。**1 テーマ = 1 コミット。** 報告を省略形にしない。§2・§3・§8 の規則は一括実行でも緩めない。
- **ゲートの出力はテーマごとに別のディレクトリ**: `TAG=<テーマID>-baseline` と `TAG=<テーマID>-final`（例: `swa-soap-baseline`）。再実行は別の名前で保存する（§5）。
- **ベースライン**: **各テーマの開始時に、必ず自分で実行する（`<テーマID>-baseline`）。前のテーマの final を引用しない。** 前のテーマの final はコミットの前の木で取った出力で、コミットの後の HEAD の出力ではない（前回の一括で、`-baseline` を省いて前のテーマの final を引用した報告が出た）。
- **各テーマの開始時**に `git status --short` が空であること。
- **テーマが中断したとき**（§1 の「途中で止まる条件」に当たった、または §3 の「提案して止まる」に当たった）: そのテーマの**未コミットの変更**を、宣言した「触るファイル」に限って `git checkout -- <ファイル>` で戻し、理由を記録して、**次のテーマへ進む**。
- **バッチ全体を止める**のは、(a) 最初のベースラインが赤、(b) 変更を戻した後も `git status --short` が空にならない、(c) 他の人の未コミット変更を見つけた、のどれか。止めた場合は、そこまでの結果と理由を報告する。
- **報告**: テーマごとの §10 の報告を `artifacts/improvement/<stamp>-reports/<テーマID>.md` に保存する。最後に、①バッチ全体の一覧表（テーマ ID・コミット・結果＝完了／中断／見送り・理由・報告ファイルのパス）と、②各テーマの §10 の報告を**そのまま続けて**出力する。報告の先頭に「読んだガイドの版」を書く（§10）。
- `git push` はしない（§3）。コミットは 1 テーマ 1 件で、後から 1 件ずつ取り消せる粒度にする。

## 2. 絶対規則（違反した提出物は内容を読まずに差し戻す）

### 2.1 実行したことだけを報告し、証拠は実行の生出力から引く

過去にこのリポジトリで起きたこと: ターミナル出力そのものの捏造（存在しないテストファイル名 17 個、バージョン番号の相違）、mutation 表に書かれた「落ちたテスト名」が実在しない、報告に書かれた CLI パスが存在しない、grep 出力が丸ごと架空。**コードは本物だったのに、報告の証拠だけが偽造された回が複数ある。** 偽造は、コードが正しくても、そのサイクル全体の差し戻し理由になる。

したがって:

- 各ゲートの出力は**ファイルに保存**する（§5 のコマンドをそのまま使う）。報告の数字・テスト名・grep 結果は、**そのファイルから引く**。手で打ち直さない。
- 出力を貼れないものは「実行できなかった」と書く。**推測で「通るはず」と書かない。**
- **報告に貼る `tsc`・`lint`・`npm test`・`build` の出力は、保存ファイルを `cat` / `tail` した結果に限る。** 別途、直接実行した出力を貼らない。貼った出力が保存ファイルと一致しないこと（例: 保存ファイルに無い警告ブロックが貼られている、`duration_ms` の数字が違う）は、証拠の不整合として扱う。
- **保存に `tee` を使わない。** `exit` の行が落ち、`tsc` のように出力が空になるゲートが、成功か失敗か保存ファイルから判別できなくなる。§5 のコマンドをそのまま使う。
- **ゲートの出力と報告は `artifacts/improvement/` に保存する。** `/tmp` は再起動で消える（実際に、一括実行の報告 9 本・ゲート出力・SW-C の分類表がすべて失われ、監査できなくなった）。
- **報告の品質ゲート欄は §5 の 4 本すべて（`npm test` は全件）。** 関連テストだけを回した結果で代えない。
- **報告・要約表に書くテストファイル名・セレクタ名・関数名は、`ls` と `git show <hash>` の diff から引く。** 記憶や推測で書かない（要約表に実在しないセレクタ名を書いた例がある）。**実行したテストコマンドの対象ファイルが存在しなければ、その結果を根拠にしない**（存在しない `useOfficialAuditSettings.test.ts` を実行して「関連テスト通過」と書いた例がある）。
- 報告に書くテスト名は `grep -n "test('" <ファイル>` で実在を確認してから書く。
- 報告に書く grep 結果は、報告を書く時点で**もう一度実行**した出力を使う。
- 報告に書く**行番号**（変異の位置など）は、最後の編集の後に `grep -n` で取り直す。編集で 1 行ずれた古い番号を書かない（実際に 68 行目と書いて 69 行目だった例がある）。
- **ゲートは `bash scripts/improvement_gate.sh <TAG>` だけで実行し、`exit` 行を残す（§5）。** 個別のコマンドを `> file` で保存したり、`tee` や合成スクリプトを使うと、`exit` 行が無くなったり、tsc と lint が欠けたり、単一ファイルになって、成功か失敗か判別できなくなる（前回の一括実行で 3 回のうち 2 回がそうだった）。報告の品質ゲート欄は 4 本すべて。
- **報告の「触らなかったが気づいた点」に書く行番号・変数名・state 名・ファイルパスは、`grep -n` / `ls` で実在を確認してから書く。** 存在しない `error` 状態を「格納されている」と書いた例がある（`useFacilitySettings`）。実画面の表の「データの状態」は、実際に件数などを測った値だけを書く。測っていなければ「未測定」と書く。
- **報告の件数・集計は、保存した表を数え直して書く。** 分類表の (b)(c) の件数を、表（23・41）と違う数（20・44）で書いた例がある。**画面の通知の有無を「なし」と書くときは、トースト領域の全文を、待ち時間を置いて読む**（SW-U-1 の報告は、実際に出ていたトーストを「なし」と書いた）。
- **報告の「変更ファイル」は `git show --stat <hash>` の出力をそのまま貼る。** 手で書かない（`0c4f2cb` は報告 158 行・実際 219 行、`4d9bbb9` も食い違った）。
- **保存した報告ファイルと、チャットに出す報告は同一の内容にする。** 保存ファイルを `cat` した結果をそのまま貼る（前回は、保存ファイルとチャットで構成も内容も食い違った）。
- **ゲートの出力から転記する数字（`duration_ms` など）は、保存ファイルに実在する値だけ。** 前回は `62890`・`62319` と書かれたが、どの保存ファイルにも無かった。**回帰ガードの「前 → 後」は、前も後もコマンドを実行して取る**（前回は全体の `: any` を「245 → 245」と書いたが、実際は 257 → 247 だった）。
- **報告・検証報告に書くコミットハッシュは、`git cat-file -t <hash>` が `commit` を返し、`git log -1 --format='%h %s' <hash>` の件名が書こうとしている内容と合うことを確かめてから書く**（存在しないハッシュ `5fc456c` を「SW-C-13 の修正」と書いた検証報告があった。実際は `b0f2162`）。**他の報告やログから引用する文言（「全件緑」など）は、元のファイルを `grep -n` で開いて原文を確かめ、原文のとおりに書く**（元の報告が EPERM の 3 本を開示していたのに「全件緑と記載」と書いた例、`console.error` のメッセージを実在しない文言で引用した例がある）。

### 2.2 偽カバレッジの禁止

- テストの中で対象ロジックを `.filter()` 等で再実装して「テストした」ことにしない。対象は純粋関数として `export` し、**本物を import** する。
- 「テストを追加した」と書く前に、そのテストファイルが対象のモジュールを import していることを `grep -n "^import" <テスト>` で確認する。
- `typeof X === 'function'` だけのテストを「描画を検証した」と呼ばない（現在 0 件。増やさない）。
- 「全体で N 件通った」は、そのモジュールの正しさの根拠にならない。
- **挙動を検査するテストが無いコード**（`typeof X === 'function'` やソースを文字列で読むテストしか無いもの）に、型付けや整理を加えるときは、**先に特性化テスト（現状の出力を固定するテスト）を足す**: 1 コミット目が `test:`、2 コミット目が `refactor:`。単体で呼べない画面コンポーネントなら、判定を純粋関数に切り出す `refactor:`（挙動不変）を先に別コミットで行ってからテストを書く。足せないときは、その理由を報告に書き、挙動が変わっていないことを diff で示す（第9サイクルの SW-E は、型付けした 2 ファイルを守るテストが無く、価格・`itemId`・`drugName` を壊す変異 4 件が全部通った）。
- **`fix:` コミットは、直す前に落ちて直した後に通るテストを伴う**（変異で確かめる）。画面ハンドラ等でテストを足せないときは、§8.1 の実画面の再現で代える。
- **テスト名は、実際に検証していること以上を名乗らない。** 「集計する」「すべて」「各」と名乗るなら、足し算と代入、1 件と全件を**区別できるフィクスチャ**にする（例: チャンクごとの失敗を集計すると名乗るテストは、失敗するチャンクを 2 つ以上にする。失敗が 1 チャンクだけだと、`+=` を `=` に変えても通ってしまった）。

### 2.3 変異を実測する。ただし「指定した変異が全部落ちた」は十分の証明ではない

§6 の 4 手順を実際に実行して表で報告する。**落ちなかったら「落ちなかった」と書き、テストの方を直す。** 落ちていないのに「落ちた」と書くのが、このリポジトリで最も重い違反である。

### 2.4 数字は実測の差で書く

コミットメッセージと報告に書く件数は、`ℹ tests` の**前回合計 → 今回合計の差**と、新規テストファイルごとの `ℹ tests N` で照合してから書く。記憶で「それらしい件数」を書かない（レビュアー自身も 7 件を 9 件と誤記して直した）。

### 2.5 食い違いを指摘されたら、記録ではなく実測を直す

過去に「9 件では」と指摘されて、9 件目を実行せずに記録の数字だけ 8 → 9 に書き換えた例がある（実際は 9 件目は原理的に検出不能で、8 が正しかった）。件数や結果の食い違いを指摘されたら、**まず実測し直し、記録を実測に合わせる。**

### 2.6 頼まれていないことをしない

- 宣言した「触るファイル」以外を変更しない。気づいた問題は**報告に書くだけ**にして、直さない。
- `refactor:` を名乗るコミットに挙動変更を混ぜない。**型付けで入力の取り出し元が変わる**（例: 存在しない `doc.drugName` を `item.dispensedDrug || item.drugId` に変える）のも挙動変更。`fix:` の別コミットに分け、報告でもそのコミットに帰属させる（第9サイクルで、`drugName` の変更が `refactor:` に混ざり、報告は別の `fix:` の説明に書いていた）。
- **`refactor:`（とくに型付け）で挙動が変わる書き換えの具体例**（`0c4f2cb`・`0718943` で実際に出た）: **既定値の追加**（`?? 1`）、**`?.` や `||` への置き換え**（`patientDoc ? patientDoc.name : '…'` → `patientDoc?.name || '…'` は、名前が空文字のときの結果が変わる）、**型ガードの追加**（`typeof x === 'number' ? x : 0` は、`x || 0` と `NaN`・文字列のときの結果が違う）、**実行時の分岐の追加**（`'token' in db` のような構造判定。偽のとき監査ログを書かない経路ができた）。型付けのために必要でも `refactor:` には入れない。**型で通す方法は、構造的な `interface` と、変換を伴わない型宣言だけ。** 通らないなら、`fix:` の別コミットにして前後の挙動の違いを報告に書くか、「判断を仰ぐ点」に書いて止まる。
- **`as X` のキャストで型を通さない**（`settingsData as FacilitySettings`、`patientDoc as Patient` など）。キャストは型の緩和と同じで、不整合を隠す。合わないなら、入力の型を `Pick<…>` や構造的な `interface` で正しく書く。
- **実画面確認の最中にテーマ外のバグを見つけたら、そのテーマのコミットに混ぜない。** `4d9bbb9` は、日次棚卸が初期リリースから常に空だったバグの回避策（`doc?.isNarcotic`）を、通知の修正に混ぜ、保存した報告には「堅牢化」とだけ書き、チャットの報告には書かず、元からのバグだとは報告しなかった。根本原因は別の場所（薬品行の組み立てが区分を写していない）にあり、検証者が `62b8f99` で直した。見つけたら、混ぜずに「触らなかったが気づいた点」へ、ファイル・行・再現手順・実画面で見えた結果を書く。
- **通知は「画面に出る」ものだけを通知と数える。** `useState` の `set…` をするだけでどこにも描画されない（読まれない）状態は通知ではない（`snapshotWarning` は set するだけの死んだ state だったが、報告は「警告バナー表示」と書いていた）。
- **触るファイルの `any` を増やさない。** 新しく書く関数の引数・戻り値に `any` を使わず、必要な最小の構造的な型（使うメソッドだけを持つ `interface`）を定義する。`: any` の全体件数は §4.2 の SW-E のコマンドで前後を取り、増えていたら報告に理由を書く（第1サイクルは 294 → 295 に増えた）。
- **型の宣言に `X | unknown` を書かない。** `unknown` に潰れて何も強制せず、戻り値を `as` キャストで読むことになる（第3・第5サイクルで 2 回出た）。戻り値の形を使うなら `Promise<BulkRemoveResultLike>` のように具体的な型にし、キャストで読まない。
- **同じ問いに答える関数を 2 つ書かない（金科玉条 第八条）。** 接頭辞や文言だけが違うなら、引数にして 1 つにする（第6サイクルで、接頭辞以外同一のメッセージ組み立て関数が 2 つできた）。
- **失敗の通知・表示を足す修正で、保存・永続化・取り消しの挙動（書き込みを止める／止めない、上書きする、保存を許可するフラグ）を変えない。** SW-C-17（`339da84`）は、復元失敗の通知を足すついでに、失敗時に保存を許可するフラグを `false` にし、以後の「発注済みにする」が無言で保存されなくなり、不正値も上書きされず、再読み込みしてもバナーが出続けた（検証者が実画面で確認し、`bcd9b34` で戻した）。保存の挙動を変えたくなったら、変えずに「判断を仰ぐ点」に書いて止まる。

## 3. 自律してよいこと／提案して止まること／絶対にしないこと

### 自律してよい（§4 の範囲内に限る）

- 失敗が利用者に伝わらない箇所に、日本語の通知（何が起きたか＋次に何をするか）を足す。**通知の手段は、そのファイルの既存の流儀に合わせる**（印刷画面 `print/[visitId]/page.tsx` は `alert`、設定のフックは `toast`）。**同じ失敗を inline のエラー表示と `alert` で二重に通知しない**（`SingleOfficialUkeModal.tsx` で二重になった）
- 書き込みの戻り値・結果を検査して、失敗を例外・通知にする
- 型を足して `any` を消す（足した型が本当の不整合を暴いたら、直さず報告 — §7）
- 呼び出し元が 0 件だと**実測した**死コードの削除
- 既存の純粋関数を切り出して本物のテストを足す
- 文字サイズを `--fs-*` トークンへ寄せる（実画面確認が条件 — §8）

### 提案して止まる（報告の「判断を仰ぐ点」に書き、実装しない）

- スキーマの追加・`version` の bump（`src/db/schema.ts`）
- **算定結果（点数）・UKE 出力・電子処方箋や機器連携の送信ペイロードが変わる変更**
- 権限（`canUserPerform` の判定）の追加・変更
- 警告の重大度の変更（warning → error、または警告を消す）
- 同期・競合解決の挙動
- 文言以外の画面導線（ボタンの追加・削除・移動）
- 新しい npm 依存の追加
- テストの `assert` 数を減らす変更
- 金科玉条で「判断待ち」「現地証跡待ち」とされた項目（§4.4）

### 絶対にしない

- `git push`、`--force`、`git reset --hard`、`--no-verify`
- `.env*` の内容の出力・コミット、IndexedDB / DB の削除
- 監査ログのハッシュチェーン（`audit_integrity.ts`）を弱める変更
- 実患者データを使った検証
- 金科玉条 第Ⅰ部の変更
- **`killall` / `pkill` で自分が起動したのではないプロセスを止めること**（`killall node` はマシン上の全 node、他のプロジェクトの dev サーバも落とす。前回の検証で 2 回実行された）。止めてよいのは自分が起動したプロセスだけで、`kill <PID>`（PID は自分の起動コマンドの戻りか `lsof -i :3000` で確かめる）と書く。ポート 3000 が既に使用中で、自分が起動したものでなければ、止めずに報告する

### 既に決着していて、再び指摘・変更しないこと

- OCR 画面の患者統合に権限チェックが無い件は、**事務職が受付画面から患者を統合・削除してよい**と決定済み。権限は足さない。
- 公式 UKE の YK レコードの登録番号は変更しない。
- `useSessionLock`、`demo_data`、設定画面の初回セットアップ CSV/メモの `await logAuditAction(` は意図的に戻り値を見ていない。
- バックアップ復旧後の監査ログ失敗は、災害復旧を止めないため取り消さず警告にしている（意図的）。
- 算定側の `isExternal = category === 'external' || EXTERNAL_USAGE_PATTERN.test(usage)` の OR は、保存値が腐った明細に対する唯一の防波堤。**外さない。**

## 4. 何に取り組むか

### 4.1 選び方

金科玉条 第Ⅲ部 §0 の優先順位に従う: **臨床安全 > 請求の正確性 > データ保全 > 本番接続の証跡 > 現場の運用効率 > コード品質。** 迷ったら、影響範囲（触るファイル数）の小さい方を先にする。

## 5. ゲート

**ゲートは `bash scripts/improvement_gate.sh <TAG>` の 1 コマンドだけで実行する。これ以外の方法（個別のコマンド、合成スクリプト、`tee`）で回さない。** 下の 4 行と同じものを、日付つきの新しいディレクトリ `artifacts/improvement/<stamp>-<TAG>/` に `tsc.txt` / `lint.txt` / `test.txt` / `build.txt`（各ファイルの末尾に `exit` 行）として保存し、`npm test` の末尾と `exit` 行を表示する。同じ名前のディレクトリがあれば何もせず止まる（赤の出力を上書きしない）。TAG は `baseline` / `final`、一括実行では `<テーマID>-baseline` / `<テーマID>-final`、再実行は `final-rerun` のように別の名前にする。サンドボックス内で `fetch failed` の 3 本が落ちたときの扱いは、下の「注意」のとおり。

## 6. 変異テスト（fail-first mutation）

各テーマで、宣言した変異を**実際に**注入する。

1. 変異を 1 行ソースへ注入する（例: `sed` や `python3` の 1 行置換）
2. **対象のテストファイルだけ**を実行し（上記の特定実行）、落ちたテスト名と件数を実測する
3. **変異を入れる前に、そのファイルのコピーを `artifacts/improvement/<stamp>-mutbak/<名前>.txt` へ取っておき、`cp` で戻す。** `git checkout -- <ファイル>` は、そのファイルに**未コミットの正しい変更**があると、それごと消す（検証者と Gemini の両方が、変異の後始末で未コミットの修正を消した）。戻したら `git diff` で、変異だけが消えて修正が残っていることを確認する
4. 同じテストを実行し、pass に戻ることを実測する

変異は **`npm run build` が完走した後**に当てる（build 中にソースを触ると壊れる）。1 件 30〜60 秒。

**「指定した変異が全部落ちた」は、テストが十分という意味ではない。** 過去に、指定した 4 つの変異はすべて検出されたのに、**変異が当たらない軸**（屯服 `as_needed` だけ表示ラベルの突き合わせが壊れていた）にテストが無く、バグが緑のまま通った。そのため、宣言に次を加える:

- 変異が**当たらない軸**を自分で 1 つ以上挙げ、その軸でテストが緑のまま壊れうるかを検討して報告に書く
- 判定に複数の分岐（列挙値）があるなら、**各分岐に 1 件ずつ**フィクスチャを入れる
- **取り消し・ロールバック・復旧を書いたら、「取り消し自体が失敗したら」を 1 軸として必ず入れる。** 失敗の再現は、例外を投げさせるだけでなく、RxDB が実際に返す形（`{ success, error }`）でも行う（§7 のコード）。「例外が投げられる」と仮定した `try/catch` だけでは、RxDB の主な失敗の形を捕まえられない（`72a9f57` はこの前提で書かれ、検証で見つかった）。
- **画面のハンドラの配線を 1 軸として必ず入れる。** `handleXxx` が判定結果を受けて `alert` して `return` する、成功時だけ入力欄をリセットする、といった分岐は、ハンドラ内の `if (false)` や `return;` の削除で壊し、**テストが落ちるか**を確かめる（`72a9f57` では、画面側の失敗分岐を丸ごと無効化しても 7 件全通過だった）。この repo には DOM を動かすテスト基盤が無く（`renderToStaticMarkup` と Puppeteer だけ）、ハンドラは単体で呼べない。したがって次の 2 つをセットにする: (1) ハンドラの分岐の判定を**純粋関数に出し**（例: `{ alertMessage: string | null; resetForm: boolean }` を返す関数）、ハンドラは戻り値に従うだけにして、その関数を本物のテストで検証する。(2) 配線（戻り値を無視していないか）は**実画面で失敗経路を再現して確認**し、報告の「実画面確認」に書く（§8.1。描画できただけは確認に数えない）。どうしても落とせない変異は、落とせないと報告する。

## 7. この repo で実際に起きた落とし穴

テストが全件緑のまま通ったものばかり。新しい書き込み・日付・描画・剤形判定を触るときは、該当する項を読んでから書く。

### RxDB の書き込み

- **同じインスタンスで `patch()` を 2 回呼ぶと必ず `CONFLICT`**。「書いて、監査が残らなければ同じ doc で戻す」取り消しは、実 RxDB では全部失敗していた。**取り消しは `src/lib/rxdb_restore.ts` の `restoreFields`（incrementalPatch）か `restoreWith`**。通常の書き込みは `patch()` のまま（他端末の変更を CONFLICT で検出するため）。
- **`patch()` は「無い項目」を消さない。** 統合などで項目が補われた記録を元に戻すときは `doc.incrementalModify(() => ({ ...record }))`（`undefined` を書くとキーが残る）。
- **複数文書の一括書き込み**は `applyReversiblePatches`（失敗したら前半を戻す）と `undoAppliedPatchesNote`（戻せなかったら警告文）。
- **`bulkInsert` / `bulkRemove` / `bulkUpsert` は個別の失敗を例外にしない**（`rx-collection.js` の `bulkRemove` は、ストレージの `bulkWrite` の結果から `{ success, error }` を組み立てて返す）。**書いた側の `{ success, error }` を検査し、取り消しの側の戻り値も検査する**。戻すのは `success` に入った ID だけ。取り消しに失敗したら、取り消せたと言わず、残っている件数を利用者に伝える。
- **失敗の再現（テスト用）**: ストレージ層で 409 を返させると、RxDB が実際に返す形で失敗を作れる（`rx-collection-bulk-remove` は検証済み。`bulkUpsert` / `bulkInsert` の文脈名は `node_modules/rxdb/dist/esm/rx-collection.js` の `storageInstance.bulkWrite(` の第 2 引数で確認する）。

  ```ts
  const storage = db.locations.storageInstance;
  const orig = storage.bulkWrite.bind(storage);
  storage.bulkWrite = async (rows: any[], context: string) =>
    context === 'rx-collection-bulk-remove'
      ? { error: rows.map((r) => ({ status: 409, isError: true, documentId: r.document.id, writeRow: r, documentInDb: r.previous })) }
      : orig(rows, context);
  ```

  `documentId` の `r.document.id` は主キー名に合わせる。他のコレクションの失敗の再現に使い回してよい。
- **`upsert` / `bulkUpsert` は文書を丸ごと置き換える。** 書き戻す項目を列挙してコピーすると、列挙し忘れた項目が更新のたびに消える（納品書取込が `priceHistory`・発注点などを消していた）。全体を書き戻すなら `drugRecordFromDocument`（`src/lib/drug_record.ts`）、在庫数だけなら `patch`。
- **`doc.claimLifecycle` のような入れ子の値は、開発ビルドで `structuredClone` できず `DOC24` で失敗**する。複製は `doc.toJSON().field` か `plainCopy`（`rxdb_restore.ts`）。Node のメモリストレージでは再現しない（再現は `rxdb_plain_copy.test.ts` の dev-mode プラグインか実ブラウザ）。
- **戻り値の形（`{ success, error }`）を手書きのモックで作ったテストだけで、「取り消しを検証した」としない。** 少なくとも 1 件は、実 RxDB（メモリストレージ）に上のストレージ層の差し替えで失敗を起こさせ、DB に実際に何が残るかまで確認する。モックのテストは、件数の集計・分割・メッセージ組み立ての確認として併用してよい。
- **取り消し・復元のテストは `src/lib/test_support/rxdb_like_doc.ts` の `RxLikeStore` で書く。** 偽ドキュメント（`patch: async (v) => Object.assign(state, v)`）は版の性質を持たず、壊れた取り消しがテストを通る。書いた後は `restoreFields` を `patch` に戻して**テストが落ちること**を確かめる。
- **スキーマにプロパティを足したら `version` を +1**（ただし §3 で「提案して止まる」）。上げ忘れてもテストは緑で、壊れるのは既存ユーザーの DB だけ。

### 監査ログ（`src/lib/audit_guard.ts`）

新しい書き込み・書き出しを足すときは、**先に 3 種のどれに当たるかを決める**:

| 種類 | 関数 | 振る舞い |
|---|---|---|
| 書き出し（CSV・ファイル・クリップボード） | `exportWithAuditFirst` | 監査 → 持ち出し。監査が失敗したら書き出さない |
| 書き込み | `runWithAuditRollback`（単一文書は `patchWithAuditRollback`） | 書込 → 監査。失敗したら元に戻す。戻せなければ `rollbackFailed` |
| 点検・結果の記録 | `recordAuditOrNotify` | 止めない。**記録が残らなかったことを通知する** |

`await logAuditAction(...)` の戻り値を捨てない（§4.2 SW-F）。「記録しました」と画面に出す前に、戻り値で分岐する。

### 日付

- `new Date().toISOString().slice(0, 10)` は **UTC の日付**。日本時間の 0:00〜8:59 は前日になる。「今日」は `toLocalDateKey()`、保存値（受付日時の ISO 文字列など）は `toLocalDateKeyFromValue()`（`src/lib/local_date.ts`）。
- `npm test` は `TZ=Asia/Tokyo` だが、既存テストの時刻は `T09:00` で UTC も同日になるため、**朝 9 時前だけの不具合は検出されなかった。** 日付のテストは `new Date(2026, 9, 8, 8, 30)` のようにローカル時刻で組み立て、**朝（0:30 / 8:30）と夜（23:59）の両方**を確認する。

### 剤形・数量

- `resolveDosageCategory` は**保存済み `dosageCategory` があれば無条件で返す**。保存値と用法が食い違う明細（古い保存値）で壊れる。剤形を触るテストには、**保存値と用法が食い違うフィクスチャ**を必ず入れる。手動指定を尊重する層は `resolveEffectiveDosageCategory`。
- **表示ラベルで剤形を比較しない。** `DOSAGE_CATEGORY_LABELS.as_needed` は `'屯服'`（屯）だが、算定側のフラグ名 `isTonpuku` から素朴にラベルを作ると `'頓服'`（頓）になり、屯服が全件「食い違い」になる。比較は `DosageCategory` の列挙値で行い、ラベルは表示の直前にだけ引く。
- 単位が無いときに `|| '錠'` のように補完しない（`amount_semantics.ts`）。

### 描画テスト

- `renderToStaticMarkup` の出力には、`<style jsx>` の **CSS 本文が素のまま `<style>…</style>` として入る**。`html.includes('is-danger')` は CSS セレクタに当たり、肯定は DOM に無くても通り、否定は誤って落ちる。**`html.replace(/<style[\s\S]*?<\/style>/g, '')` で除去してから**検証する。`disabled` は `disabled=""` で照合する。
- `Received true for a non-boolean attribute jsx` の警告は無害。
- 変異で「クラス名を変えたら落ちるか」を 1 件は確かめる。
- `useRouter` などで静的描画できないものは、純粋関数（判定＋文言）と表示専用の `…View` に分けてテストする。

### スタイル

- Vanilla CSS と CSS 変数のみ。**Tailwind 等は使わない。** 文字サイズは `src/app/globals.css` の `--fs-2xs`(12px) / `--fs-xs`(13px) / `--fs-sm`(14px) / `--fs-md`(15px) / `--fs-base`(16px)、余白は `--space-*`。**生の rem を書かない。**
- `styled-jsx` は**書かれたコンポーネントのスコープにしか効かない**。同一ファイル内の別コンポーネントに同じクラス名を付けても、エラーも警告も出ず無スタイルになる。複数コンポーネントで共有するクラスは `globals.css` へ、ただし `.insurance-modal .modal-header` のように固有の祖先クラスで囲う。
- 文言は日本語。エラー文は「何が起きたか」と「次に何をするか」を書く。英語のエラーをそのまま出さない。

### 分割・モジュール化（`refactor:` の検証）

過去、巨大ページの分割で元のロジックが取り違えられ、`tsc`・build・既存テストが全部緑のまま回帰した（印刷時の薬剤師確認 6 種中 5 種が消えた、など）。`refactor:` を名乗るなら、**初期リリース `8091090` の元ページ（`git show 8091090:src/app/<page>.tsx`）と突き合わせる**: 元ページの日本語文言が現在の `src` 全体に残っているか、`build*/format*/make*` の呼び出しの引数の数、`make*FileName` の出力形式、元ページが import していた関数が今どこからも使われていないか。

## 8. 画面を変えるときの実画面確認

単体テストで見えないバグ（保存されない、常に null、常に空）は実画面でしか見つからない。**見た目や操作が変わるテーマ（SW-A など）は、実画面確認が完了条件。** 「確認した」の自己申告ではなく、**何を操作して何を見たか**を報告に書く。

- **サンドボックスで Chrome や dev サーバの起動が `spawn EPERM` / `Permission denied` で拒否されたら、ゲートの再実行と同じようにサンドボックスの外で実行する**（SW-C-16・17 の実画面確認はそれで動いた）。止めるときは自分が起動したプロセスの PID だけ（`killall` / `pkill` は使わない — §3）。
- 開発サーバ: `npm run dev`（:3000）。起動直後は初回コンパイルで遷移がタイムアウトするので、先に主要ページを一度開いて温める。
- 幅 **1280 / 768 / 375px** の 3 つで確認し、横スクロールのはみ出しが 0px であること。既存の通しドリル: `node scripts/run_e2e_accessibility_drill.mjs`。
- 印刷帳票の回帰: `npm run test:e2e:print-layout`（**dev サーバ必須。`next start` では動かない**）。`element.boundingBox()` が 180 秒でハングすることがあるが、**コードの回帰と決めつけない**。失敗時も `artifacts/print-layout-regression/<stamp>/page.html` は保存されるので、中身は grep で確認できる。
- onboarding E2E: `YAKUREKI_E2E_AUTO_SEED=1 node scripts/runOnboardingE2E.mjs`（dev サーバ必須）。初回は各ページのコンパイル待ちで「missing selectors」になりやすい。失敗時の `page.html` に中身が出ていればタイミング失敗なので、そのまま再実行する。
- Puppeteer の詰まりどころ:
  - `page.click(selector)` は画面下方の要素でハングする → `page.$eval(sel, el => el.click())`
  - `window.confirm` を出すボタンを `page.evaluate` の中から押すと詰まる → `page.on('dialog')` を付け、evaluate の**外**から押す
  - 値を入れて blur させるときは、先に `el.focus()` を呼ぶ（フォーカスが無いと `onBlur` 保存が動かない）
  - Chrome が見つからないとき: ダウンロードせず `PUPPETEER_EXECUTABLE_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"`
  - 医薬品マスター CSV は Shift_JIS で読まれる（UTF-8 だと列名照合に失敗する）
  - スクリプトはプロジェクト直下に置かないと `node_modules` を解決できない。**終わったら消す。**
- 書き込み失敗の再現: `crypto.subtle.digest` を reject させると「監査ログが残らない」状況を作れる。ただし `page.goto` のたびに元に戻るので、遷移した後に入れ直す。`db.<collection>.bulkInsert` を差し替えれば、一括書き込みの部分失敗を再現できる。利用者に何も出ない失敗は、`alert` と `[data-sonner-toast]` と pageerror を見て確かめる。

### 8.1 画面のハンドラを変えたときの確認（失敗経路の再現は必須）

**描画できた・ボタンを押せた、だけは確認に数えない。** 画面の書き込みハンドラ（保存・一括作成・取り消しなど）を変えたテーマは、**失敗の経路を再現して、利用者に見えるものを記録する**。単体テストではハンドラ本体を呼べない（この repo には DOM を動かすテスト基盤が無い）ので、ここが配線の唯一の守りになる。

1. **失敗の再現**（`db.<collection>` の書き込みを差し替える）と、**成功の対照**（差し替えを外す）の両方を実行する。
2. シナリオごとに、(a) `alert` / トーストの**文言そのまま**、(b) 入力欄・画面の状態（保たれたか、リセットされたか）、(c) データの状態（件数など）を記録する。
3. **ハンドラの分岐に変異を 1 件当てて**（例: `if (outcome.resetForm)` → `if (true)`、`if (outcome.alertMessage)` → `if (false)`）、同じ確認の結果が**変わる**ことを確かめる。変わらなければ、その確認は配線を守っていない。確認後は §6 の手順 3 のとおり、バックアップから `cp` で戻す（`git checkout` は未コミットの修正を消す）。
4. **実画面で見えた不具合が、このテーマの変更によるものか、元からのバグかを区別する。** 元からのバグなら §2.6 のとおりコミットに混ぜず、報告の「触らなかったが気づいた点」に書く（変更前のコードに戻して再現するのが確実）。

手順（動作確認済みのやり方）:

- `npm run dev` を起動し、`/` と対象ページを一度開いて温める。Puppeteer の Chrome は `PUPPETEER_EXECUTABLE_PATH` で指す。
- `/` の `button[data-testid="pre-login-tour-start-guest-demo"]`（または `.btn-resume-demo`）でデモを始め、対象ページへ遷移し、タブは `page.$eval(sel, (el) => el.click())` で開く（`page.click` は下方の要素でハングする）。
- **db の取り出し**: 対象セクションの DOM 要素の `__reactFiber$…` から子孫をたどり、`memoizedProps.db.<collection>` を持つ fiber を探して `window.__db` に置く。
- **失敗の差し替え**: `window.__db.<collection>.bulkInsert = async () => ({ success: [], error: [{ documentId: 'x', status: 409 }] })`。部分失敗なら `success` に `{ id: 'a' }` などを入れ、取り消しの失敗は `bulkRemove` も `{ error: [...] }` を返すよう差し替える。戻すときは `delete window.__db.<collection>.bulkInsert`。
- **入力**: `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set.call(el, 値)` のあと `el.dispatchEvent(new Event('input', { bubbles: true }))`（React の `onChange` が動く）。`aria-label` で要素を探す。
- **alert の取得**: `page.on('dialog', (d) => { messages.push(d.message()); d.accept(); })`。
- スクリプトはプロジェクト直下に置く（`node_modules` を解決するため）。**終わったら削除する。** macOS には `timeout` コマンドが無い。`evaluateOnNewDocument` で `localStorage` を触ると `about:blank` で `SecurityError` が pageerror に出るが、アプリの不具合ではない。
- 終わったら dev サーバを止める。

### 8.2 見た目だけを変えるテーマ（CSS・文字サイズ・余白）の確認

ハンドラを変えないテーマでも、**変更前後の実測**を表にする。「描画できた」は確認に数えない。第8サイクルで有効だった方法:

1. **変更前後の計算済みスタイルを、同じスクリプトで測る。** 変更後を測り、次に変更前の CSS へ一時的に戻して（`git show <コミット>^:<ファイル> > <ファイル>`）同じ測定をして、戻す（`git checkout -- <ファイル>`）。測るものは、対象要素の `getComputedStyle(el).fontSize`、`getBoundingClientRect()` の幅と高さ、`document.documentElement.scrollWidth - document.documentElement.clientWidth`（横スクロール）。幅 1280 / 768 / 375px。
2. **デモデータに出てこない要素（例: 代替薬の展開）は、プローブ要素で測る。** 対象のクラス名の `<span>` を `document.createElement` で画面に差し込み、計算済みスタイルを読んで、読んだ直後に取り除く。クラス名のスタイルが効いていること（CSS 変数が解決されて期待どおりの px になること）を、データに依存せず確かめられる。
3. **375px で折り返しが「変更前からあった」のか「変更で新たに生じた」のか**を、変更前の測定と比べて書く。
4. 測り終えたら、`git status --short` が空であること、dev サーバを止めたこと、スクリプトを消したことを確認する。
5. データが再現できず測れなかった要素は、「測れなかった」と理由を書く（プローブで測れた場合はそう書く）。**一括実行の最後の要約表にも「未検証」と残し、「検証済み」と書かない**（例: `SingleOfficialUkeModal` のコピー失敗は、デモデータでは公式UKEが請求前チェックエラーになり、コピーのボタンが出ず測れなかった）。

## 11. レビューでは何が確認されるか

提出物は、あなたの報告を信じずに次の手順で検証される。**報告を書く前に自分でも同じことをしておく**と、差し戻されない。

0. **報告の「読んだガイドの版」が、レビュー時点の `git log -1 --format=%h -- docs/gemini_continuous_improvement_guide.md` の出力と一致するか**、報告の見出しが現行の §10 のテンプレートか、`tee` を使っていないか、`-baseline` / `-final` のディレクトリがあるかを確認する。版が無い・古い・見出しが旧テンプレートなら、**改訂前のガイドで動いた**と判定して、内容を読まずに差し戻す。 **証拠ファイル（報告・ゲート出力・分類表）が `artifacts/improvement/` に残っているか**、**要約表のコミット説明（セレクタ名・関数名・テストファイル名）が `git show` の diff と一致するか**も見る。保存先に無い、または説明が diff と食い違う報告は、監査不能・不正確として差し戻す。
1. `git log` で実コミットを確認し、`tsc` / `lint` / `npm test` / `npm run build` を**最初から自分で再実行**する。報告の数字は転記しない。
2. 報告に貼られたコマンド出力の真偽: パッケージ名・バージョン、`npm test` の実スクリプト文字列との一致、`suites` 数と `duration_ms` が実測レンジ（約 120 suites・約 60〜210 秒。マシンの負荷が高い日は 700 秒を超える）に収まるか、**保存ファイルの内容と一致するか**、出力に出てくるファイル名が `find` で実在するか。
3. 変異表の「落ちたテスト名」を `grep -n "test('" <ファイル>` の実在文字列と照合する。
4. 報告が貼った grep 出力・ファイルパスを、当該コミットの親（`git grep <語> <hash>^`）から取り直して突き合わせる。
5. 変異を 2〜3 件、独自に注入してテストが落ちるかを確認する。**報告が挙げた「当たらない軸」の前提が正しいかも確認する**（例: 「例外が投げられる場合」と書かれていれば、実際の失敗の形が例外か戻り値かを RxDB のソースで確かめる）。報告が挙げなかった軸、**取り消し自体の失敗**と**画面ハンドラの配線**は、必ず自分で当てる。
6. 画面・ハンドラを変えたテーマは、**報告の「実画面確認」が失敗経路を再現しているか**を見る（描画とクリックだけなら未確認として扱う）。自分でも失敗の差し替えとハンドラへの変異を当てて、確認結果が変わるかを確かめる。

## 付録 A: 握りつぶし `catch` の候補を出すスクリプト（SW-C 用）

`catch` ブロックを波括弧で切り出し、**利用者への通知・再 throw・エラー状態のセット等が一切無い**ものを列挙する。**候補を出すだけで、判定はしない。** 実測: 183 件（精度は高くない。分類は §4.2 SW-C）。

rows = []
for p in sorted(pathlib.Path('src').rglob('*')):
    if p.suffix not in ('.ts', '.tsx') or '.test.' in p.name:

    t = p.read_text(encoding='utf-8')
    for m in re.finditer(r'\bcatch\b\s*(\([^)]*\))?\s*\{', t):
        i, depth = m.end(), 1
        while i < len(t) and depth:
            depth += (t[i] == '{') - (t[i] == '}')
            i += 1
        body = t[m.end():i - 1]
        if not NOTIFY.search(body):
            rows.append(f"{p}:{t.count(chr(10), 0, m.start()) + 1}  {' '.join(body.split())[:90]}")
print(len(rows))
print('\n'.join(rows))
PY

- **V2 diff を読む**: (a) 失敗を表す state が JSX から**読まれて**いるか（`set…` するだけの state は通知ではない）、(b) 失敗を表す prop が必須か（`?` や既定値で渡し忘れを型が止めない形になっていないか）、(c) `refactor` の混入（既定値、`?.`、`||`、型ガード、`as X`、実行時の分岐の追加。関数を切り出したなら、通常時の出力が変更前と同一か）、(d) 失敗から復旧したとき（再読み込み・対象の切り替え・モーダルの開き直し）に state が戻る位置、(e) 非同期の `effect` で古い結果が新しい結果を上書きしないか（cancel フラグ）、(f) 本番のコードから使われない口（テストだけが使う prop など）、(g) 同じ画面・同じ関数に同形の `catch` が他に無いか（`git grep`。直さず記録）。
- **V3 変異**: 元の報告の変異を、バックアップ付きで再現する（落ちた件数とテスト名）。そのうえで、**報告が挙げなかった軸**で 2 件以上を自分で当てる（判定の優先順、リセットの位置、境界、`role` / `disabled` などの属性）。生き残った変異は、「低価値」か「要対応」かを理由つきで記録する。
- **V4 実画面（最大の目的）**: 元の報告の実画面は全件「未確認」。**失敗の再現・成功の対照・復旧・配線の変異**の 4 つを、画面に見える文言と状態で記録する（描画できた・押せた、だけは確認に数えない）。配線の変異は、画面側で失敗 state を渡す 1 行（例: `hasError={x}` → `hasError={false}`）を壊し、同じ失敗の再現で表示が元の空表示・無表示に戻ることを確かめる。
- **V5 回帰ガード**: §4.2 の SW-F の 5 つの数字と `: any` / `as any` を、親コミット（`git grep -h … <hash>^ -- src | wc -l`）と HEAD で取り直す。
- **V6 触らなかったが気づいた点**: 行番号・識別子は `grep -n` で取り直したものだけを書く。

### 実画面の手順（検証者が 2026-10-17 に SW-C-11〜15 で動作確認済み）

- 実行環境: Puppeteer（`PUPPETEER_EXECUTABLE_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"`）。**Chrome の起動で `spawn EPERM` / `Permission denied (1100)` が出たら、ゲートの再実行と同じように、サンドボックスの外で実行する。** それでも起動できないときだけ「未確認」とし、そのエラー出力を貼る（他のテーマの出力を使い回さない）。
- デモの開始: `/` で `.btn-resume-demo`（または `button[data-testid="pre-login-tour-start-guest-demo"]`）をクリック。デモ患者は「デモ患者 みどり」（`pt_demo_tutorial`、1958/05/12、受付あり）。ページ遷移は `a[href="/emr"]`・`a[href="/ocr"]`・`a[href="/"]` の `.click()`（クライアント遷移）。**`page.goto` や再読み込みは、後述の差し替えを消す。**
- DB の取り出し: 対象ページの DOM 要素の `__reactFiber$…` から `return` をたどり、`memoizedProps.value` が `soap_records` と `visits` を持つ fiber を探して `window.__db` に置く。
- 失敗の差し替え: `db.<collection>.find` / `findOne` / `findByIds` を、同期的に `throw` する関数に差し替える（元の関数は退避して戻す）。患者に紐づくときだけ失敗させるなら、引数の `selector.patientId` を見て分岐する。**差し替えは `effect` が再実行されるまで効かない**ので、`/` と `/emr`（または `/ocr`）の間をクライアント遷移で往復するか、画面の操作（モーダルを開く、患者を選び直す）で再実行させる。
- トースト: `MutationObserver` で `[data-sonner-toast]` の `innerText` を配列に溜める（同じ文言は 1 回だけ記録）。時間差で消えるので、操作の後に待ってから読む。
- OCR（`/ocr`）: 「OCRなしで手入力受付」を押すと患者欄が出る。`#patientName` に「デモ患者 みどり」、`#patientBirthDate` に「19580512」を、`Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,'value').set.call(el, 値)` のあと `el.dispatchEvent(new Event('input',{bubbles:true}))` で入れる。候補は `.patient-candidate`、選択ボタンは `.patient-candidate-select`、処方の入力は `input[aria-label="処方薬品名 1"]`。患者を選び直して `effect` を再実行するには、別の候補（デモ患者 一郎）を選んでから戻す。
- EMR（`/emr`）: ピッキング支援のようにモーダルは**開かないと DOM に無い**ものがある。モーダルは開いてから読む。
- 配線の変異（実画面）: 変異の前に `cp` でバックアップし、Fast Refresh の反映を数秒待ってから同じ失敗の再現をやり直し、終わったら `cp` で戻して `git status --short` が空であることを確かめる。複数の独立した画面の配線変異を、同じファイルに同時に入れてもよい（画面の別の場所で判別できるとき）。
- ダイアログ: `window.confirm` を出すボタンは、`page.on('dialog')` を付けたうえで、`page.evaluate` の**外**から押す（§8）。
