## 3. 新規の指摘

### N-1【要対応】P1-4 に挙動の安全網がなく、Phase 1 と Phase 2 の順序が逆転している

`src/app/settings/page.tsx` をソース文字列として読み込んでいるテストは **10 ファイル / assert 623 箇所**です。

```
src/app/SettingsBackup.test.ts               src/app/SettingsAudit.test.ts
src/app/SettingsDrugDuplicateReview.test.ts  src/lib/auth.test.ts
src/app/SettingsStaffAudit.test.ts           src/lib/browser_backup_export_job.test.ts
src/app/SettingsAuditExportOrder.test.ts     src/lib/onboarding_e2e.test.ts
src/app/SettingsExternalConnector.test.ts    src/app/SettingsTerminalSync.test.ts
```

**設定画面を覆っているテストはこれで全部**であり、いずれも挙動を検証していません（ソース文字列への正規表現マッチのみ）。

したがって P1-4 で 124 の `useState` を hook へ移動させると：

1. 623 箇所の assert が壊れる
2. **壊れたことは機能後退の証拠にならず、壊れないことも無事の証拠にならない**
3. 巻き添えの手修正が P1-4 の工数に含まれていない

一方、テスト移行タスク P2-2 は Phase 2、すなわち **P1-4 の後**に置かれています。計画中で最大の状態リファクタリングを、挙動の安全網ゼロで実施する順序になっています。

**指示**: 設定画面に限り、P2-2 の①分類（純粋関数の抽出 ＋ 直接 import テスト）を **P1-4 の直前へ前倒し**すること。hook を切り出すのと同一コミットで本物のテストを書き、対応するソース文字列 assert を削除する。623 箇所を「後で直す」形で残さないこと。P1-4 の工数 3.5 人日はこの前倒し分を含んでいないため、再見積が必要です。

同じ構造の依存が P2-1（print / ocr / emr）にも存在します。P2-1 と P2-2 は gantt 上で並走していますが、**画面ごとに「テスト①分類 → hook 抽出 → JSX 分割」の順で閉じる**ことを明記してください。

### N-2【要対応】§2.2 の図に同種の誤りがもう 1 箇所残っている

ノードラベル（`RxDB_Mem`）は修正されましたが、エッジラベルが未修正です。

```
RxDB_Mem -- "HTTP Bearer / AES-GCM Push/Pull" --> API
```

`PHARMACY_SYNC_TRANSPORT_ENCRYPTION` の既定値は `src/lib/env.ts:81` で `'none'`、`.env.example:117` の出荷値も `none` です（`aes-gcm` は L119 でコメントアウトされた任意設定）。図が既定でない安全性を主張しており、**今回是正したのと同じ種類の誤り**です。

**対応**: エッジラベルを「HTTP Bearer / 既定は平文（`aes-gcm` は任意設定）」等に修正するか、既定値を `aes-gcm` に変更する提案として §5 に論点として上げること（後者は設定済み環境への影響があるため独断で変更しないこと）。

### N-3 論点 1 の選択肢 (a) はハブトークン由来だと自己矛盾する

「暗号鍵をハブ接続時の動的トークン由来に切り替える」を採ると、**ハブに接続できない状態で端末を再起動した際にキューを復号できません**。これはキューが存在する理由そのもの（クラッシュ・スリープ・端末再起動時のデータ喪失防止、`satellite_local_queue.ts` の docstring）を破壊します。

スタッフ入力パスワード由来であれば成立しますが、フラッシュ前に必ずパスワード入力を要求することになり、§3.2-3 が課題として挙げている「ハブ故障時の朝イチ復旧」の場面で運用摩擦が増えます。選択肢として提示する際は、この可用性コストを明記してください。

## 4. P1-3 の前提を確定（レビュー者による実機確認）

前巡 §A-4 では「Turbopack が既定のため `webpack:` 設定が効いていない**可能性が高い**」と留保しましたが、実機で確定させました。

- `.next/turbopack` ディレクトリが生成されている → **本番ビルドは Turbopack を使用**（Next 16.2.3 の既定）
- `npx next build --help` に `--webpack`（webpack でビルド）オプションが存在し、既定でないことが確認できる

したがって `next.config.mjs` の `webpack:` ブロック内 `config.resolve.fallback = { fs: false, path: false }` は **本番ビルドに適用されていません**。P1-3 は「可能性の精査」ではなく「確定した死に設定の処理」であり、以下の二択で 0.5 人日は妥当です。

1. `webpack:` ブロックを削除する
2. `--webpack` フォールバックを維持する意図があるなら、その旨をコメントで明示して残す

なお初版 §2.1 の「Turbopack 最適化ビルド」という記述自体は**正しかった**ことになります。前巡でこの点に疑義を呈したのはレビュー者の誤りでした。

## 5. 論点 1 への回答（リード判断）

サテライト端末ローカルキューのセキュリティモデルについて、以下の通り決定します。

### 決定: **(c) を必須、(b) を採用、(a) は現時点で不採用**

現行モデル（localStorage への AES-256-CBC 暗号化キュー、鍵は同一 localStorage に同居）を、下記 (b)(c) を条件として **現状のまま許容します**。

#### (a) 鍵導出の変更 — 不採用

§3 N-3 の通り、ハブトークン由来は自己矛盾。スタッフパスワード由来は成立するが、障害時の運用摩擦が可用性要件（§3.2-3）と衝突する。(b) の運用実績を見てから再検討する。

#### (b) 保持期間・件数のハードリミット — 採用（Phase 2 に組み入れること）

- 保持期間の上限（例: 当日閉局時まで）と最大件数の上限を設ける
- 上限超過時は明示的な警告 UI を出し、放置を検知可能にする
- 実装コストが小さく、患者データがローカルに露出している時間を実際に短縮する

#### (c) ドキュメント・アーキテクチャ定義の整合 — 必須（即時）

- §2.2 のノードラベルは修正済み。**エッジラベルが未修正**（§3 N-2）
- **運用マニュアル側にも記載が必要**: サテライト端末のブラウザプロファイルには、フラッシュ完了までの間、患者データ（`patients` / `visits` / `soap_records` / `prescription_items` / `alerts` / `interventions`）が暗号化状態で残存する。**端末の廃棄・返却・貸与・修理出しの際にプロファイル消去を必須手順とすること**。実装コストゼロで、現行モデルにおいて最も効果の大きい統制である
