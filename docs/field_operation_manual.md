# pharma-oss 現場運用マニュアル

このマニュアルは、店舗で毎日システムを操作するスタッフ（薬剤師・事務）向けの手順書です。
「いつ・誰が・どの画面で・何をするか」を業務の時間割に沿ってまとめています。
機能ごとの詳しい説明は [取扱説明書（user_manual.md）](user_manual.md)、開発・保守は [developer_manual.md](developer_manual.md) を参照してください。

> **実請求前の注意**: 電子レセプト（UKE）出力は、公式仕様との突合と返戻ケースの検証が完了するまで実請求に使用しないでください（設定 > レセプト点検 で未検証項目を確認できます）。

権限の割り当ては「設定 > 初回セットアップ > 権限ロール設定」で店舗の運用に合わせて調整できます。

## 2. 開局前チェック（毎朝 5分）

1. **端末とログイン**: 各端末でアプリを開き、自分のアカウントでログインします。共有アカウントは使いません。
   - 複数端末の店舗では**メイン端末を最初に起動**します（アプリ本体に加えて、同期ゲートウェイも起動しておきます。§10）。サテライト端末は起動時にメイン端末からデータを取得するため、メイン端末が動いていないとログイン画面まで進みません。ログイン後、画面上部の同期表示が「同期済み」であることを確認します。
2. **ダッシュボード確認**: 「要対応」表示（バックアップ未完了・返戻・期限超過フォロー）が残っていないか確認します。
3. **前日のバックアップ**: ダッシュボードまたは「設定 > バックアップ」で、前日の暗号化バックアップと外部保存確認が記録済みであることを確認します。未完了なら開局前に実施します。
4. **復旧通知の確認**: 画面にデータベース復旧が必要な通知が出ている場合は操作を止め、管理者がバックアップからの復旧手順（user_manual §3.8）を実施します。
5. **マスタ更新の予定確認**: 薬価改定や医薬品マスター更新の予定日であれば、開局前に「設定 > マスタ更新」で取り込み、差分CSVとロールバックJSONを保管します。

## 3. 受付〜完了の基本フロー（1患者ごと）

### 3.1 受付
- **紙処方箋**: 「処方箋OCR」で読み取り、患者・処方元・薬品・用法を目視確認して確定します。OCR信頼度が低い項目は必ず原本と照合します。
- **手入力**: OCRなし受付では氏名と生年月日で既存患者へ名寄せされます。保険番号だけで判断しません。
- **電子処方箋**: **現在は未実装です**（接続モジュールが無く、画面のボタンは押せません）。紙の処方箋か処方箋QRで受付してください。接続モジュール導入後は、受付入力の「電子処方箋」欄から取得します。「処方内容（控え）」だけを見て調剤しないでください（詳細は user_manual §3.3）。
- 受付が終わると、患者はダッシュボードの対応キューに載ります。

### 3.2 ピッキング
1. ダッシュボードから患者を開き、棚番地順のピッキングリストで薬品を集めます。
2. **GS1照合**: 現物のGS1バーコードをスキャンし、薬品・ロット・期限の一致を確認します。未照合が残ると「GS1未照合」フラグが表示されます。
3. **棚不足があったら**: その場で「不足を記録」します。記録した不足は発注ワークベンチの候補に自動で載ります。あとでまとめて、ではなくその場で記録します。
4. **既存ピッキングシステムを使う店舗**: ピッキング支援画面の「指示CSV」を書き出してシステムへ渡し、払出後に「結果取込」で結果CSVを取り込みます。完了行は照合済みに、不足行は不足記録に反映されます。取り込んだ後は、現物とロット・期限が一致しているか必ず確認してください。院内でGS1照合済みの明細は外部結果で上書きされません。

### 3.3 処方監査・薬剤師確認（薬剤師）
1. 患者アラート（アレルギー・副作用歴）、相互作用、重複投薬の警告を確認します。
2. **要修正（赤）**: 解消するまで印刷・UKE出力へ進めません。処方修正または疑義照会で解消します。
3. **薬剤師確認（黄）**: 内容を確認し、問題なければ理由を残して先へ進みます。
4. 疑義照会をした場合は、変更内容・医師回答を記録します（薬歴・調剤録・レセプト摘要に連動します）。

### 3.4 薬歴（SOAP）
1. EMR画面で前回薬歴と処方差分を確認してから服薬指導します。
2. SOAPを入力します。AI下書きは補助であり、**保存前に薬剤師が必ず内容を確認・修正**します。
3. 服薬フォローが必要な患者は、フォロー候補に理由と次回確認日を残します。

### 3.5 印刷・会計・完了
1. 印刷画面で調剤録・薬袋・薬情・お薬手帳シール等を出力します。
2. 未完了の確認事項が残っていると完了できません。表示に従って解消します。
3. 完了操作で在庫が引き落とされ、患者が完了一覧へ移ります。

## 4. 閉局時チェック（毎日 10分）

1. **対応キューを空にする**: 処理中・監査待ちの患者が残っていないか確認します。残す場合は理由をチームで共有します。
2. **サテライト端末の同期確認**: 複数端末の店舗では、各サテライト端末の画面上部が「同期済み」であることを確認してからタブを閉じます（未同期のまま閉じると入力が消えます。閉じる際に警告が出ます）。サテライトを閉じたあとにメイン端末を終了します。
3. **日次締め**: ダッシュボードの日次締めで、完了件数・在庫不足・フォロー候補・残タスクを確認し、承認します。
4. **バックアップ**: 「設定 > バックアップ」で暗号化バックアップを書き出し、店舗で定めた外部保存先へ置き、「外部保存を記録」します。**メイン端末で実施すれば全端末分が含まれます**。自動化している店舗は、状態JSONと失敗通知が出ていないかを確認します（user_manual §6）。
5. **発注**: 発注ワークベンチで当日の不足候補を確認し、発注済みへ更新します。

## 5. 月次業務（月初・月末）

1. **レセプト（UKE）**: 月次請求ワークベンチで対象受付を確認し、請求前チェックの指摘をすべて解消してから月次一括UKEを作成します。停止された場合は確認CSVの内容に従って修正します。
2. **受付結果取込・返戻対応**: 審査結果を「結果取込」で反映し、返戻は返戻修正メモと差分CSVで対応します。
3. **監査ログの外部保全**: user_manual §5 の手順で監査ログJSONと保全台帳CSVを出力・保管し、棚卸CSVで不足がないことを確認して責任者承認します。
4. **バックアップ世代確認**: user_manual §6 の手順で3世代以上・暗号化・復旧テスト30日以内を確認します。
5. **患者重複点検（名寄せ）**: 「設定 > バックアップ > 患者重複点検」で「重複候補を確認」を実行し、同姓同名・同生年月日の重複患者がいないか確認します。重複があれば、受付履歴の多い患者を「残す患者」にして統合します（統合は監査ログに残ります）。移行直後の店舗は月1回、安定後は四半期に1回が目安です。
   あわせて「設定 > マスタ更新 > 薬品重複点検」で、使用中薬品の重複（在庫や処方参照が2つのコードに割れている状態）がないかも確認します。マスタ更新の後に実施するのが効果的です。
6. **月次レビュー**: 日次締め月次レビューでKPI（返戻・在庫不足・フォロー・問い合わせ）を確認し、改善アクションを決めます。

## 6. 練習用デモデータの使い方

新人研修や操作練習には、チュートリアルのデモ患者を使います。**実患者で練習しないでください。**

1. 画面右上の「3分デモ」を開き、最後のステップで「**デモ患者で体験を始める**」を押します。
2. 投入される練習データ（すべて「デモ」表記・固定ID付き）:
   - デモ患者 みどり（副作用歴アラート付き: ロキソプロフェンで胃部不快感）
   - 本日の受付1件（処方3剤。3剤目はわざと在庫不足で、不足記録の練習ができます）
   - 前回来局（28日前）の完了受付と薬歴 — 履歴参照・前回Do・処方差分の練習用
   - 在庫ロット（棚番地・JANコード付き）— GS1照合の練習用
3. 受付→ピッキング→薬剤師確認→薬歴→印刷まで、実際の画面で一通り練習できます。
4. **請求への安全装置**: デモ受付はUKEファイル出力・月次一括UKE・外部調剤機器連携の対象になりません。誤って実請求へ混ざることはありません。
5. **練習後の片づけ**: 「3分デモ」最後のステップの「**デモデータを片づける**」で、デモ患者・受付・処方・薬歴・アラート・在庫を一括削除します。削除は監査ログに残ります。デモデータが残っている間はダッシュボード上部に片づけを促すバナーが表示され、そこからも同じ削除を実行できます。日次締めの前に必ず片づけてください。
6. 投入・削除は何度でも安全に繰り返せます。研修のたびに投入→練習→片づけ、を1セットにしてください。

このほか、処方箋受付・ピッキング・薬歴入力の各画面には、保存されない「業務別30秒デモ」もあります（初回に自動表示・画面上のデモボタンで再表示）。

## 7. 困ったとき（トラブル対応）

| 症状 | まずやること | それでも直らないとき |
|---|---|---|
| 画面が固まった | ブラウザの再読み込み（F5）。入力途中のデータは自動保存されている場合があります | 端末再起動。復旧通知が出たら管理者へ |
| データベース復旧の通知が出た | **操作を止める**。他端末での入力も止める | 管理者がバックアップから復旧（user_manual §3.8）。自己判断でブラウザデータを消さない |
| OCRの精度が悪い | 明るい場所で影なく撮り直す。低信頼度項目は原本照合 | 手入力受付へ切り替え |
| UKE出力が止められた | 画面の指摘・確認CSVの内容を1件ずつ解消 | 解消できない指摘は責任者へ。無理に出力しない |
| 在庫が合わない | ロット・期限単位で現物照合し、不足はその場で記録 | 棚卸差異として記録し、原因（返品・破損・記録漏れ）を確認 |
| 端末の故障・紛失 | 予備端末でログインし業務継続（データは各端末のローカルDB + バックアップ） | 最新バックアップから復旧。紛失時は管理者がスタッフ認証情報を再設定 |
| **サテライト端末**の故障・紛失 | 他の端末で業務継続。**紛失時は未送信キュー等の残存データがあるため個人情報漏えい事案として扱う**（管理者への即時報告・記録） | 管理者がメイン端末の「設定 > 端末同期」で対象端末のトークンを失効（Revoke）させ、アクセスを即座に遮断する |
| **サテライト端末**の廃棄・返却・修理出し | **端末のブラウザプロファイル完全消去**（設定 > プライバシー > サイトデータ/Cookie/localStorage を全削除）を必ず実施 | メイン端末の「設定 > 端末同期」で対象端末のトークンを失効（Revoke）させる。未送信データが残存したまま第三者へ渡るリスクを完全に遮断する |
| サテライト端末に「メイン端末未接続」が出た | 入力は続けられます。**そのタブを閉じない**（未送信の入力が消えます）。メイン端末の起動（アプリ本体と同期ゲートウェイの両方）とLAN接続を確認 | メイン端末復旧後、画面上部が「同期済み」に戻ったことを確認してから閉局する |
| メイン端末が起動しない | サテライトで入力を続けつつ（タブは閉じない）、管理者がメイン端末を復旧 | 復旧不能なら予備機へバックアップ復旧し、各サテライトの「設定 > 端末同期 > 予備機切替」で接続先を切り替える（§7.1） |
| 「暗号化キーを保存できないため…」と出て起動しない | プライベートブラウズ終了、保存領域（localStorage）許可、空き容量確保のうえ再読み込み（サイトデータの削除は厳禁） | 直らなければ管理者へ（§7.2）。患者データは消えていません |
| スタッフ退職・パスキー紛失 | 「設定 > 初回セットアップ > 復旧・退職対応」で対象と理由を選んで対応 | 最後の管理者は削除不可。復旧レビューは `npm run staff:access-recovery-review` |

**絶対にやってはいけないこと**
- メイン端末での安易なブラウザの履歴・キャッシュ・サイトデータの削除（患者データが消えます。バックアップと復旧確認なしでは実施しない）
- サテライト端末の廃棄・返却・修理出し時にブラウザプロファイル消去を怠ること（フラッシュ前の未送信データが残存するリスクがあります）
- 復旧通知が出た状態での入力継続
- デモ以外の実患者データでの練習
- サテライト端末で「メイン端末未接続」表示のままタブを閉じる・端末を再起動する（未送信の入力が消えます。画面上部が「同期済み」になってから）

---

### 7.1 メイン端末が復旧できないとき（予備機への切替）

管理者が行います。切替は**サテライトごと**です。メイン端末の状態を確かめてから始めてください。

**事前（平常時・年1回のリハーサルを含む）**
1. 各サテライトで「設定 > 端末同期 > 予備機切替」を開き、予備機の URL（例: `https://standby-hub.local:3443`、同期ゲートウェイの URL）を「新規予備Hub の事前登録」に入れて「登録 (HMAC署名発行)」を押します。メイン端末と通信できているときだけ登録できます。
2. 予備機は、メイン端末のハブストア（`PHARMACY_SYNC_HUB_DB_PATH` の SQLite ファイル）を閉店時バックアップから復旧して用意します。**端末の登録（トークン）はこのファイルの中にある**ので、ファイルごと復旧すれば各サテライトは同じトークンのまま使えます。ブラウザのバックアップだけを復旧した予備機には端末の登録が無く、切替は拒否されます（その場合は予備機側で端末を登録し直し、各サテライトの `.env` を更新して再起動します）。

**メイン端末の故障時**
1. 予備機を起動し、同期ゲートウェイも起動します（メイン端末と同じ設定。`PHARMACY_SYNC_HUB_ENCRYPTION_KEY` と転送暗号化の設定も同じ値）。
2. 各サテライトで「予備機切替」から予備機を選び「選択した予備機へ接続先を切り替える」を押し、確認の文面を読んで進めます。切替の前に、予備機がこの端末を受け付けること・スタッフ情報が復旧済みであることが自動で確かめられ、満たさなければ拒否されて何も変わりません。
3. 切替後、画面の「現在の接続先」が予備機になり、同期の表示が「同期済み」に戻ることを確かめます。切替は端末を再起動しても保たれます。

**知っておくこと**
- 予備機はバックアップ時点の内容です。**バックアップより後の入力は予備機にありません。** 切替の時点でサテライトのタブに残っている内容は、予備機に無いものは予備機へ送られます。同じ項目が予備機にもあって内容が違う場合は予備機の内容が採用され、サテライト側の内容は予備機の「設定 > 端末同期」の競合レビューに残ります（確認して必要なら入力し直してください）。
- 切替は、この端末のタブを閉じずに行ってください（閉じると、予備機に無い入力が失われます）。
- メイン端末が復旧したら、各サテライトで「メイン端末（既定）へ戻す」を押します。戻すときも同じ扱い（メイン端末に無いものは送られ、食い違う項目はメイン端末の内容が採用）です。予備機のまま運用を続けると、メイン端末とは別の正本になります。
- 接続先の保存先は `PHARMACY_SYNC_SATELLITE_STATE_PATH`（既定 `./data/satellite_hub_state.json`）です。このファイルを消して再起動すると、`PHARMACY_SYNC_HUB_ENDPOINT` の接続先に戻ります。

### 7.2 起動時に「暗号化キーを保存できない」と表示されるとき

起動時に「ローカルデータベースを開けません」と「このブラウザでは暗号化キーを保存できないため、データベースを開けません。プライベートブラウズを終了するか、ブラウザの保存領域（localStorage）の利用を許可して、再読み込みしてください。」（詳細: QuotaExceededError や 詳細: SecurityError）が表示される場合の対応です。

- **原因**: ブラウザが暗号化キーを保存できない状態（プライベートブラウズ、保存領域の空き容量不足、ブラウザ設定での保存遮断など）です。
- **まずやること**: プライベートブラウズを終了する、ブラウザのサイトデータ（保存領域）を許可する、端末の空き容量を確保する、を実施した後にページを再読み込みしてください。**ブラウザのサイトデータ削除は絶対にしないでください**（患者データが消えます）。
- **データ保全**: 患者データは消えていません。アプリは自動削除や自動初期化を一切行いません。保存領域を使える状態に修復すれば開きます。直らなければ管理者へ連絡してください（メイン端末復旧不能時は §7.1 の予備機切替へ）。
- **旧バージョンDBの扱い**: `NEXT_PUBLIC_DB_PASSWORD` 未設定で作成された旧バージョンDB（共通の旧固定鍵）を継続使用している端末は、保存領域が使えると自動で新しい仕組みに移行して開きます（保存される鍵は旧固定鍵）。保存領域が使えない場合は以前と異なり起動を停止します（旧固定鍵での自動開き直しはしません）。必ず保存領域を利用可能な状態にして起動してください。
- **管理者向け**: 本番環境では `NEXT_PUBLIC_DB_PASSWORD` を設定してください（README・.env.example 記載。設定済み環境では保存領域の鍵を使いません）。旧固定鍵のままの DB は、バックアップを書き出し、`NEXT_PUBLIC_DB_PASSWORD` を設定した環境で復旧して新しい鍵へ移行してください。

## 8. 緊急復旧用 暗号鍵エスクローシートの保管・運用規程

メイン端末のブラウザプロファイル破損、端末ハードウェア障害、またはデータ全損事故が発生した際、データベースを安全に復元するために「**緊急復旧用 暗号鍵エスクローシート（A4）**」を発行・保管します。

### 8.1 セキュリティ設計の前提（必ず理解すること）
1. **復号の前提条件**: エスクローデータは、発行時点の「**管理者パスワード**」を用いて **PBKDF2 (120,000回 SHA-256) ＋ AES-GCM-256** で暗号化されています。
2. **強度の依存性**: **エスクローの安全性は管理者パスワードの強度に完全に依存します。** バックアップJSONや紙面シートが存在しても、強力な管理者パスワードがなければ復号できません。逆に、管理者パスワードが脆弱または漏洩した場合、バックアップや紙面シートから全データが復号されるリスクがあります。

### 8.2 紙面シートの発行・保管・管理基準
- **発行手順**:
  - **方法A（印刷）**: 印刷画面の「9. 緊急復旧用 暗号鍵エスクローシート」で管理者パスワードを入力して発行し、A4印刷。
  - **方法B（ファイル出力）**: 「設定 > バックアップ」画面の「暗号鍵エスクロー（緊急復旧）管理」セクションにある「① 緊急復旧用シートを発行・保管」で管理者パスワードを入力し、テキストファイル（`emergency_key_escrow_XXXX.txt`）をダウンロードして印刷。
- **保管場所と施錠**: 発行した紙面シートは、必ず**耐火金庫等の鍵のかかる安全な保管庫**で管理責任者（管理薬剤師・管理者）が厳重に施錠保管してください。
- **無断複製の禁止**: コピー機、カメラ、スマートフォンによる紙面シートの無断複製・デジタル化保存は固く禁止します。
- **廃棄・失効手順**:
  - 管理者パスワードを変更した場合や、端末・DBの鍵ローテーションを実施した場合は、旧シートを**直ちに業務用シュレッダーで完全物理裁断廃棄**してください。
  - 放置や一般ゴミへの廃棄は厳禁です。
- **紛失時の対応**:
  - 万が一シートを紛失した場合は、速やかに管理者に報告し、全端末で管理者パスワードの変更およびDB暗号鍵の再暗号化・ローテーションを実施してください。

### 8.3 復旧時の手順
1. 新規端末または初期化されたブラウザでシステムを起動。
2. 「設定 > バックアップ」画面を開く。
3. 「暗号鍵エスクロー（緊急復旧）管理」セクションの「**② エスクローからDB暗号鍵を復元**」フォームに、紙面シート記載の「エスクロー暗号化ペイロード（Base64またはJSON）」を貼り付け。
4. 発行時の管理者パスワードを入力し、「**暗号鍵を復元して適用**」を押下。
5. 復元成功メッセージ（Fingerprint一致確認）を確認後、画面を再読み込みして復旧したDBにアクセス。

## 10. ネットワーク・端末の導入チェックリスト（管理者）

複数端末の店舗では、導入時と、ルーターや端末を入れ替えたときに確認します。

### 10.1 ネットワーク
- [ ] 業務端末（メイン端末・サテライト端末）は、**来客用Wi-Fiとは別のネットワーク**に置く（ルーターのゲスト用Wi-Fi機能、または別のルーターを使う）
- [ ] メイン端末のIPアドレスを、ルーターの**DHCP予約**で固定する（変わるとサテライトの接続先が切れる）
- [ ] メイン端末のOSのファイアウォールで、同期ゲートウェイの待受ポート（既定 3443）への受信を、**サテライト端末のIPアドレスだけ**に許可する。それ以外の受信は許可しない
- [ ] プリンタ・POS・スタッフの私物端末など、業務に使わない機器は業務端末と同じネットワークに入れない

### 10.2 起動の仕方
- [ ] **全端末**: アプリ本体は `npm run start` で起動する。メイン端末・サテライト端末の設定（`PHARMACY_SYNC_ROLE` が `hub` または `satellite`）では、自動で「この端末の中だけで受け付ける起動」になる（`npm run start:local` と同じ）。`next start` を直接起動しない
- [ ] **メイン端末**: 本体を起動したあと、`npm run sync:gateway` で同期ゲートウェイを起動する。起動時に「LAN側アドレスでも待ち受けています」と表示されて止まったときは、本体を `npm run start` で起動し直す（`next start` を直接使っていないか確認する）
- [ ] **メイン端末**: 同期ゲートウェイは HTTPS で公開する。証明書と秘密鍵のパスを設定する（手順は developer_manual の「店舗内複数端末」）
- [ ] **切り替えの注意**: これまでメイン端末で `npm run start` を使っていた店舗は、切り替え後、サテライトからメイン端末の本体へ直接はつながらなくなる。同期ゲートウェイを起動し、各サテライトの接続先を下のURLに変更する
- [ ] **サテライト端末**: 接続先（`PHARMACY_SYNC_HUB_ENDPOINT`）は、メイン端末のゲートウェイのURL（`https://<メイン端末のIP>:3443`）にする。自己署名の証明書を使うときは、サテライトの本体を起動する環境に証明書を登録する

### 10.3 導入後の確認
- [ ] サテライト端末でログイン画面まで進み、ログイン後に画面上部が「同期済み」になる
- [ ] **業務用ネットワークの外**（来客用Wi-Fiにつないだスマートフォンなど）から、メイン端末のアドレス（`https://<メイン端末のIP>:3443` と `http://<メイン端末のIP>:3000`）を開き、**画面が表示されず、応答がない**こと
- [ ] 確認した日と担当者を、導入記録に残す

### 10.4 端末のディスク暗号化
- [ ] 全端末で、OSのディスク暗号化（Windows は BitLocker、Mac は FileVault）を有効にする
- [ ] OSのログインパスワードを設定し、一定時間の無操作で画面をロックする
- 端末を紛失・盗難されたときに、保存された患者データを守る最後の備えは、ディスク暗号化とOSのログインです（§7 の紛失時の対応とあわせて確認します）。
